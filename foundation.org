* System Architecture
** High-level serving pipeline
#+begin_example
Client (HTTP/gRPC/Python API)
  -> Entry point (launch_server / Engine)
  -> TokenizerManager (tokenization, multimodal preprocess, request state)
  -> Scheduler (batching, policy, cache-aware admission, forward orchestration)
  -> Model Executor (prefill/decode forward on device)
  -> DetokenizerManager (token -> text streaming)
  -> Client response
#+end_example

** Process model (runtime)
From ~python/sglang/srt/entrypoints/engine.py~ (~Engine~ docstring):
- TokenizerManager runs in main process.
- Scheduler runs in subprocess.
- DetokenizerManager runs in subprocess.
- IPC is ZMQ-based via dedicated ports.

** Design intents visible in code
- Continuous batching and overlap path in scheduler loop.
- Cache-aware scheduling (LPM/DFS) integrated with radix prefix cache.
- Pluggable execution modes and feature mixins:
  - disaggregation (prefill/decode split)
  - speculative decoding
  - LoRA dynamic loading
  - DP/PP attention paths
  - multiplexing and metrics/tracing hooks

* Core Execution Path
** Engine and subprocess orchestration
File: ~python/sglang/srt/entrypoints/engine.py~
- ~Engine~ launches tokenizer manager and scheduler/detokenizer subprocesses.
- Initializes template manager and ZMQ sockets.
- Exposes generation/embedding/admin-facing runtime APIs.

** TokenizerManager responsibilities
File: ~python/sglang/srt/managers/tokenizer_manager.py~
- Parses/normalizes incoming request payloads.
- Tokenizes text and prepares multimodal payloads.
- Maintains per-request state for streaming, logprobs, and completion tracking.
- Communicates tokenized requests to scheduler; receives partial outputs.

** Scheduler main loop contract
File: ~python/sglang/srt/managers/scheduler.py~
- Canonical cycle is represented by methods around:
  - ~recv_requests()~
  - ~process_input_requests()~
  - ~get_next_batch_to_run()~
  - ~run_batch()~
  - ~process_batch_result()~
- Mixins compose behavior for metrics, profiling, DP/PP paths, output processing,
  runtime checks, and weight updates.

** Model execution handoff
Files: ~python/sglang/srt/model_executor/*~
- Scheduler forms batch metadata and dispatches to model runner.
- Two dominant forward phases:
  - prefill/extend (prompt ingestion)
  - decode (autoregressive token-by-token generation)

* Scheduler Deep Dive
** Composition
~Scheduler~ inherits from multiple mixins, including:
- ~SchedulerOutputProcessorMixin~
- ~SchedulerUpdateWeightsMixin~
- ~SchedulerProfilerMixin~
- ~SchedulerMetricsMixin~
- ~SchedulerDisaggregationDecodeMixin~
- ~SchedulerDisaggregationPrefillMixin~
- ~SchedulerMultiplexMixin~
- ~SchedulerRuntimeCheckerMixin~
- ~SchedulerPPMixin~
- ~SchedulerDPAttnMixin~

This shape lets the scheduler keep a single event loop while attaching optional
features without moving the loop contract.

** Policy engine
File: ~python/sglang/srt/managers/schedule_policy.py~
- Cache-aware policies:
  - ~lpm~ (longest prefix match)
  - ~dfs-weight~
- Cache-agnostic policies:
  - ~fcfs~, ~lof~, ~random~, ~routing-key~
- Key behavior:
  - Computes prefix matches via radix cache for waiting requests.
  - Applies optional in-batch prefix-caching heuristics.
  - Reorders waiting queue based on policy and priority controls.

** Scheduler <-> cache coupling
- Scheduling logic reads:
  - prefix lengths (~match_prefix~ results)
  - evictable token capacity (~evictable_size~, ~full_evictable_size~, etc.)
- Admission decisions are therefore cache-state-sensitive, not pure queue order.

* Radix Cache and Memory Subsystem
** Radix tree core
File: ~python/sglang/srt/mem_cache/radix_cache.py~
- Main types:
  - ~RadixKey~: token sequence + optional ~extra_key~ (e.g., LoRA/cache salt).
  - ~TreeNode~: tree structure, value pointers, lock/host refs, metrics fields.
  - ~RadixCache~: implementation of prefix cache operations.

** Critical operations
- ~match_prefix(...)~:
  - finds longest matched token prefix in device cache
  - returns indices and relevant nodes for subsequent scheduling/execution
- ~insert(...)~:
  - inserts new token pages/segments into tree
- ~evict(...)~:
  - evicts leaves by configured policy when space is required

** Eviction strategies
Configured in ~RadixCache~:
- ~lru~, ~lfu~, ~fifo~, ~mru~, ~filo~, ~priority~
(via ~mem_cache/evict_policy.py~ strategy classes).

** Cache variants and hierarchy
- ~hiradix_cache.py~: hierarchical cache behavior (device/host/storage).
- ~swa_radix_cache.py~: sliding-window attention variant.
- ~mamba_radix_cache.py~: variant for Mamba/SSM style needs.
- ~radix_cache_cpp.py~ + ~cpp_radix_tree/*~: C++ accelerated tree path.

** Memory pools and initialization parameters
- ~mem_cache/cache_init_params.py~ provides cache init contract:
  - ~req_to_token_pool~
  - ~token_to_kv_pool_allocator~
  - ~page_size~, eviction policy, metrics/event toggles, etc.
- Pools and allocators live in ~memory_pool.py~, ~allocator.py~, and host/cache
  coordination via ~memory_pool_host.py~, ~cache_controller.py~.

** 2) Scheduler policy tuning
#+begin_src bash
python -m sglang.launch_server \
  --model-path meta-llama/Llama-3.1-8B-Instruct \
  --schedule-policy lpm \
  --chunked-prefill-size 4096 \
  --max-running-requests 256

policy overhead is not worth it for a workload.

** 3) Cache behavior controls

* Troubleshooting Playbooks
** OOM during prefill or large context runs
- Lower ~--mem-fraction-static~.
- Lower ~--chunked-prefill-size~.
- Reduce ~--max-running-requests~.
- Consider smaller TP/DP footprint depending on topology.

** High queueing latency / request retractions
- Increase scheduling conservativeness (~--schedule-conservativeness~).
- Revisit policy (~lpm~ vs ~fcfs~) based on real prefix locality.
- Tune ~--max-running-requests~ and ~--max-prefill-tokens~.

** Low cache hit value
- Validate prompt prefix reuse patterns for workload.
- Confirm cache is enabled and page size/policy are sensible.
- Inspect whether request-specific ~extra_key~ separation (e.g., LoRA variants)
  is reducing reuse by design.

** Runtime hangs or long-running forward batches
- Set/adjust ~--watchdog-timeout~ and optional soft watchdog.
- Enable request logging and metrics for phase-level timing visibility.

** ForwardBatch key fields (~forward_batch_info.py~)
~ForwardBatch~ carries all per-forward-pass state.  Tensor shapes use the
convention:
- ~[num_tokens]~  — flattened across all sequences in the batch
- ~[batch_size]~  — one entry per sequence

Core fields:
- ~forward_mode~: ~EXTEND~ | ~DECODE~ | ~MIXED~ | ~IDLE~ | ~TARGET_VERIFY~ | ~DRAFT_EXTEND~ | ~SPLIT_PREFILL~ | ~DLLM_EXTEND~
- ~input_ids [num_tokens]~, ~positions [num_tokens]~
- ~seq_lens [batch_size]~, ~out_cache_loc [num_tokens]~ (KV write pointer)
- ~req_pool_indices [batch_size]~ (index into req_to_token_pool)
- ~mrope_positions [3, num_tokens]~ — Qwen-VL multi-head RoPE
- ~mamba_track_indices / mamba_track_mask~ — Mamba SSM state tracking
- ~spec_info~ — speculative decoding metadata
- ~capture_hidden_mode~: ~NULL~ | ~LAST~ | ~FULL~
- ~global_num_tokens_gpu [dp_size]~ — for DP attention coordination
- ~pp_proxy_tensors~ — pipeline-parallel hidden state passthrough
- ~encoder_lens [batch_size]~ — encoder-decoder models
- ~lora_ids [batch_size]~ — per-sequence LoRA adapter selection

** CudaGraphRunner design (~cuda_graph_runner.py~)
- Captures one ~torch.cuda.CUDAGraph~ per batch-size bucket (default: 1,2,4,8,16,32,64,128).
- Reverse capture order enables CUDA memory pool sharing across graphs.
- ~freeze_gc()~ prevents GC-induced kernel launches during recording.
- At runtime: ~populate_from_forward_batch()~ → ~graph.replay()~ → extract output buffers.
- If ~capture_hidden_mode~ differs from captured mode, the graph must be re-recorded.
- Speculative decoding: ~TARGET_VERIFY~ graphs capture ~num_tokens_per_bs × batch_size~ tokens.

** PiecewiseCudaGraphRunner design (~piecewise_cuda_graph_runner.py~)
- Uses ~torch.compile~ (inductor/eager backend) per *token-count* bucket, not batch-size.
- Compiles only ~model.language_model.model~ (embedder stays eager).
- No actual CUDA graph recording — captures lazy compilation artifacts.
- Better for variable-length prefill; avoids huge static graphs.
- Mutual exclusion: cannot coexist with ~--enable-torch-compile~, PP>1, DeepEP/Mooncake MoE.

** CPUGraphRunner design (~cpu_graph_runner.py~)
- ~torch.compile(dynamic=False)~ enforces static shapes, no CUDA memory management.
- Must register ~torch.library.register_fake()~ stubs for custom CUDA ops.
- Only supports ~dp_size=1~, ~pp_size=1~, no TP gather features.

** GraphInputBuffers design (~input_buffers.py~)
Pre-allocated fixed tensors backing CUDA graphs.  Key design points:
- ~seq_lens_cpu~ is kept on CPU — some attention kernels branch on it from host.
- ~num_token_non_padded [1]~ lets kernels skip padded buffer positions.
- Population at runtime: ~populate_from_forward_batch()~ copies real data into fixed buffers
  and fills unused slots with fill values.
- ~global_num_tokens_gpu [dp_size]~ coordinates DP attention token counts.

** Hook system (~hook_manager.py~)
~register_forward_hooks(model, hook_specs)~ attaches PyTorch ~register_forward_hook~
via fnmatch patterns, e.g. ~"model.layers.*.mlp"~.  Each spec provides a
~hook_factory~ callable (loaded by dotted import path) that produces the actual hook.

** KV cache sizing (~model_runner_kv_cache_mixin.py~)
~get_cell_size_per_token()~ computes bytes/token for pool allocation:
- MHA: ~num_kv_heads × (head_dim + v_head_dim) × num_layers × dtype_bytes~
- MLA (DeepSeek): ~(kv_lora_rank + qk_rope_head_dim) × num_layers × dtype_bytes~
  plus FP4 scale overhead and NSA indexer if applicable.
- Hybrid SWA: weighted sum of full-attention and sliding-window layers.

Pool types: ~MHATokenToKVPool~, ~MLATokenToKVPool~, ~NSATokenToKVPool~,
~DoubleSparseTokenToKVPool~, ~HybridLinearKVPool~, ~SWAKVPool~.

** DeepSeek MLA chunked prefix mixin (~forward_batch_deepseek_mha_mixin.py~)
For long-context DeepSeek MLA, breaks prefix KV cache into 256K-token chunks.
Per-chunk metadata: ~starts [num_chunks, bs]~, ~seq_lens [num_chunks, bs]~,
~cu_seq_lens~, ~max_seq_lens~, ~kv_indices~.  Allows attending to arbitrarily
long prefixes while staying within kernel memory limits.

** Process topology
#+begin_example
HTTP Client
    ↕ HTTP/SSE (JSON)
FastAPI  (http_server.py)
    ↕ async/await (in-process)
TokenizerManager  (tokenizer_manager.py)
    ↕ ZMQ PUSH-PULL IPC (pickle)
Scheduler  (scheduler.py)
    ↕ ZMQ PUSH-PULL IPC (pickle)
Detokenizer  (detokenizer_manager.py)
    ↕ ZMQ PUSH-PULL IPC (pickle)
TokenizerManager  →  HTTP client (SSE stream)
#+end_example

Scheduler also drives TP workers (same or separate processes via ZMQ broadcast).

** Stage 1 — HTTP entry (~http_server.py~)
~POST /generate~ → ~async generate_request(obj: GenerateReqInput)~.
- For streaming: returns ~StreamingResponse~ (SSE, ~text/event-stream~).
- For non-streaming: ~await __anext__()~ on the async generator.
- Serialization: orjson in/out.

** Stage 2 — TokenizerManager (~tokenizer_manager.py~)
#+begin_src python
async def generate_request(obj):
    obj.normalize_batch_and_arguments()
    tokenized = await self._tokenize_one_request(obj)   # text → token IDs
    state = self._send_one_request(obj, tokenized)       # push to scheduler via ZMQ
    self.rid_to_state[obj.rid] = state                   # track per-request state
    async for response in self._wait_one_response(state):
        yield response      # streams JSON chunks to HTTP layer
#+end_src
State uses an ~asyncio.Event~ to wake the wait loop when detokenizer pushes output.

** Stage 3 — Scheduler event loop (~scheduler.py~)
#+begin_src python
def event_loop_normal():
    while True:
        recv_reqs = self.recv_requests()           # ZMQ PULL, non-blocking
        self.process_input_requests(recv_reqs)     # → handle_generate_request()
        batch = self.get_next_batch_to_run()       # scheduling policy
        if batch:
            result = self.run_batch(batch)
            self.process_batch_result(batch, result)
#+end_src
~handle_generate_request()~: creates ~Req~, checks RadixAttention prefix cache,
adds to waiting queue.
~get_next_batch_to_run()~: applies policy, mixes EXTEND+DECODE (continuous batching).

** Stage 4 — Model execution (~tp_worker.py~ + ~model_runner.py~)
#+begin_src python
# scheduler.py
worker_batch = batch.get_model_worker_batch()
result = self.model_worker.forward_batch_generation(worker_batch)
#+end_src
Inside ~model_runner.forward()~:
1. Check CUDA graph eligibility → ~graph_runner.replay()~  (fast decode path)
2. Else prefill → ~piecewise_cuda_graph_runner.replay()~ or eager ~model.forward()~
3. Returns ~ModelRunnerOutput(logits_output, can_run_graph)~

** Stage 5 — Sampling (~model_runner.py~)
#+begin_src python
def sample(logits_output, forward_batch):
    sampling_info.update_regex_vocab_mask()
    sampling_info.apply_logits_bias(logits_output.next_token_logits)
    next_token_ids = self.sampler(logits_output, sampling_info, ...)
    return next_token_ids    # [batch_size]
#+end_src
Sampling parameters (temperature, top_p, top_k, grammar masks) are batched tensors —
each sequence can have distinct values.

** Stage 6 — Output processing (~scheduler_output_processor_mixin.py~)
- Appends ~next_token_ids~ to ~req.output_ids~.
- Checks stop conditions (EOS, max_tokens, stop strings).
- Sends ~BatchTokenIDOutput~ to detokenizer via ZMQ PUSH.

** Stage 7 — Detokenizer (~detokenizer_manager.py~)
- Receives ~BatchTokenIDOutput~ (token IDs).
- Incrementally decodes only new tokens (handles UTF-8 surrogate pairs).
- Sends ~BatchStrOutput~ (decoded text strings) back to tokenizer via ZMQ PUSH.

** Stage 8 — Response to client
TokenizerManager receives ~BatchStrOutput~, sets ~state.event~, ~_wait_one_response~
yields the chunk, http_server.py emits SSE frame:
#+begin_example
data: {"text": "Hello", "finish_reason": null, "usage": {...}}

data: {"text": " world!", "finish_reason": "stop", "usage": {...}}

data: [DONE]
#+end_example

** Data structure pipeline
#+begin_example
GenerateReqInput            (HTTP JSON → Python)
  ↓ tokenize
TokenizedGenerateReqInput   (+ input_ids: List[int])
  ↓ scheduler creates
Req                         (internal state, kv cache ptr, output_ids)
  ↓ batched into
ScheduleBatch               (many Reqs, ForwardMode)
  ↓ converted to
ForwardBatch                (GPU tensors: input_ids, positions, out_cache_loc …)
  ↓ model produces

  ↓ scheduler streams
BatchTokenIDOutput          (rids + new token IDs)
  ↓ detokenizer decodes
BatchStrOutput              (rids + decoded text strings)
  ↓
HTTP JSON response
#+end_example

** The four dispatch methods

~forward_decode()~ (line ~2174~):
- Optionally re-inits pdmux decode backend metadata.

~forward_extend()~ (line ~2197~):
- Checks ~piecewise_cuda_graph_runner.can_run(fb)~ → ~replay()~.
- Falls back to eager ~model.forward()~.
- Passes ~input_embeds~ if multimodal, ~get_embedding=True~ if not generation.
- Returns ~(output, can_run_graph)~.

~forward_idle()~ (line ~2237~):

** Weight update methods (RLHF / online training workflows)

| Method                           | Transport          | Use case                          |
|----------------------------------+--------------------+-----------------------------------|
| ~update_weights_from_disk()~       | File I/O           | Hot-reload from checkpoint        |
| ~update_weights_from_distributed()~ | NCCL broadcast    | Training→inference weight sync    |
| ~update_weights_from_tensor()~     | Shared mem / ZMQ   | In-process or IPC tensor transfer |
| ~send_weights_to_remote_instance()~ | NCCL broadcast   | Disaggregated serving weight push |

parameters into one flat tensor for a single large broadcast instead of N small ones.
